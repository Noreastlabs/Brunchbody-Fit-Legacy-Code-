# Feedback Intake Structure - 2026-06-13

## Intake Goal

Feedback intake should help triage beta issues without collecting private app data by default. Feedback should stay focused on observable behavior and wording.

## Feedback Category

- Broken flow: a screen, button, navigation path, or save action did not work.
- Confusing copy: wording around privacy, export, Delete local data, backup, release readiness, or help was unclear.
- Data-control concern: the user could not tell what was local, exported, deleted, or externally managed.
- UX friction: a primary task was slow, crowded, inaccessible, or hard to repeat.
- Release blocker: a problem prevents beta expansion, store-prep review, or owner signoff.

## Submission Guidance

Ask for screen name, steps to reproduce, expected behavior, actual behavior, app version if known, device/platform if known, and whether the issue repeated. Do not request sensitive health details, exported files, screenshots with private details, journal content, profile details, or nutrition details unless the tester chooses to provide them.

## Triage

Route feedback through Support & Contact or release/tester materials. Tag privacy wording, export/delete wording, local-first behavior, and release-readiness issues separately so disclosure-sensitive work is not lost in general bug triage.

## Non-Claims

This structure does not create cloud support, remote recovery, remote deletion, medical review, or analytics collection.
